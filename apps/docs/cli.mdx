## `postcraft dev`

Starts a local development server that will watch your files and automatically rebuild
your postcraft template when you make changes.

**Options**

<ResponseField name="--dir" type="string" default="postcraft">
  Change the directory of your postcraft templates.
</ResponseField>
<ResponseField name="--port" type="string" default="3000">
  Port to run dev server on
</ResponseField>

**F.A.Q**

<AccordionGroup>
  <Accordion title="Where can I place my static files for previewing?">
    Almost always you will need to have static files in your postcraft, and seeing
    them on the preview server without having to first host on a CDN is very helpful.

    We do allow for this, and currently, you can place your files inside a `static`
    directory inside your `postcraft` directory.

    This does adjust to your `--dir` option, so if your `postcraft` directory was inside
    `./src/postcraft`, you would place your static files inside `./src/postcraft/static`.

    These static files are directly served from our preview server by looking into the
    requests made into it that end with `/static` (i.e. `http://localhost:3000/static/...`) and serving the files at that point,
    this also allows for you to have images inside your postcraft like so:

    ```jsx
    export default function Postcraft(props) {
      return (
        <div>
          <img src="/static/postcraft-logo.png" />
        </div>
      );
    }
    ```

    <Info>
      This does not mean your images are hosted for you to send the postcraft.

        If you do send the rendered postcraft, and you are trying to link to an image,
        or some other asset inside `postcraft/static`, they will not load on the postcraft that was sent.

        We recommend that you use a different source link to your files depending on whether you're
        running in production or not. Here's an example

        ```jsx
        const baseURL = process.env.NODE_ENV === "production" ? "https://cdn.com" : "";

        export default function Postcraft(props) {
          return (
            <div>
              <img src={`${baseURL}/static/postcraft-logo.png`} />
            </div>
          );
        }
        ```

        You can refer to our [demo postcraft source code](https://demo.postcraft/preview/Community/notifications/vercel-invite-user)
        for an example of how we do this with our demo deploy on Vercel.
    </Info>

  </Accordion>
  <Accordion title="How can I define props specific to the postcraft's preview?">
    Considering that you are already default exporting the React component
    that will render as your postcraft template, you can just define a `PreviewProps` with it as follows:

    ```jsx Postcraft template
    export default function Postcraft(props) {
      return (
        <div>
          <a href={props.source}>click here if you want candy 👀</a>
        </div>
      );
    }

    Postcraft.PreviewProps = {
      source: "https://www.youtube.com/watch?v=dQw4w9WgXcQ",
    };
    ```

    And then, when opening this postcraft's preview, the `PreviewProps` will be used as props into Postcraft.
    So, in a nutshell, it will render the same as if you were to do:

    ```jsx Another file
    import Postcraft from "./path-to-my-postcraft";

    <Postcraft {...Postcraft.PreviewProps} />;
    ```

  </Accordion>
  <Accordion title="How to make the preview server ignore directories?">
    Once the preview server has started and is now open on `localhost`, the preview server
    reads recursively down into all of your files and directories. This can be disabled
    from a directory down by prefixing it with `_`, e.g. `components -> _components`.

    So if you wanted to make components for your postcraft, you could have a file structure as follows:

    ```bash
    my-project
    ├── emails
    │   ├── _components
    │   │   └── this-is-not-going-to-appear-in-the-sidebar.tsx
    │   ├── postcraft.tsx
    │   └── static
    ├── package.json
    └── tsconfig.json
    ```

    Then the only file that will be shown on the preview server is going to be your `postcraft.tsx`.

  </Accordion>
  <Accordion title="The heuristics for files to be considered postcraft">
    To avoid uncanny files appearing in the sidebar of the preview server,
    we account for two heuristics to determine weather or not we should
    include it:

    1. If a file has `.js, .jsx or .tsx` as their file extension
    2. If the file contains a `export default` expression by matching with the regex<br/>
      `/\bexport\s*default\b/gm`

    These can certainly fail as they are only heuristics, so if you do find
    any issues with these, feel free to open an [issue](https://github.com/resend/postcraft/issues).

  </Accordion>
</AccordionGroup>

## `postcraft build`

Copies the preview app for onto `.postcraft` and builds it.

<ResponseField name="--dir" type="string" default="postcraft">
  Change the directory of your postcraft templates.
</ResponseField>
<ResponseField name="--packageManager" type="string" default="npm">
  Package manager to use on the installation of `.postcraft`.
</ResponseField>

## `postcraft start`

Runs the built preview app that is inside `.postcraft`.

## `postcraft export`

Generates the plain HTML files of your postcraft into a `out` directory.

<Info>
  A very common misconception is to assume that `postcraft export` is the default or primary way of rendering
  postcraft templates.

  The primary and preferable way is always going to be the [render](/utilities/render) utility,
  by passing in the needed data through props, on the exact moment of sending the postcraft.

  `postcraft export` is a secondary way meant for situations where Postcraft cannot be used optimally.
  With this secondary way, comes significant drawbacks, mainly the need for manual templating, which
  could be done easily with the `render` utility. It being a secondary way, we would strongly recommend
  you don't use it unless you really are forced into it.

  As an example, two cases where `postcraft export` makes itself necessary include:
  - When the postcraft content must be processed by a backend in a language other than JavaScript.
  - When the platform handling postcraft, such as Shopify, forces you into manual templating.

  You also should not have to worry about `render`'s performance, as typically, the introduced
  time in rendering is going to be milliseconds when compared to manual templating.
</Info>

**Options**

<ResponseField name="--outDir" type="string" default="out">
  Change the output directory.
</ResponseField>
<ResponseField name="--pretty" type="boolean" default="false">
  Minify or prettify the generated HTML file.
</ResponseField>
<ResponseField name="--plainText" type="boolean" default="false">
  Set output format as plain text.
</ResponseField>
<ResponseField name="--dir" type="string" default="postcraft">
  Change the directory of your postcraft templates.
</ResponseField>

## `postcraft help <cmd>`

Shows all the options for a specific command.

## `postcraft resend setup`

Sets up a configuration in your home directory with your Resend API Key by prompting interactively.

## `postcraft resend reset`

Removes your API Key from the configuration in your home directory.
